ANIMACORE · ANIMATOOL — 설계 의도

코어는 자기가
어떻게 실행되는지 모른다

게임 런처와 에디터가 같은 core::Scene을 씁니다. 각자 구현하는 것은 Loop() 하나입니다. 이 페이지는 그 경계를 어디에 두었고 왜 그렇게 나눴는지를 다이어그램으로 정리했습니다.

설계 원칙
게임을 만드는 동안
엔진 코드를 수정할 필요가
없어야 한다

지난 엔진에서 얻은 원칙입니다. 게임을 만드는 동안 엔진을 계속 고쳤습니다. 급한 기능은 엔진 안에 직접 넣고, 일부 값은 하드코딩했습니다. 그런 수정이 쌓이면서 그 게임 하나에만 맞는 엔진이 되었고, 다른 게임에 다시 쓰기 어려운 상태가 됐습니다.

이번 엔진은 규칙을 하나 정하고 시작했습니다. 게임 코드가 늘어나도 엔진 코드는 수정하지 않는다. 그 조건에서 확장의 자유도를 어떻게 확보할지 정리한 결과가 코어 · 게임 로직 · 실행 파일 · 툴 네 갈래 구조입니다. 아래 다이어그램은 이 규칙을 지키기 위해 택한 방법들입니다.

01

모듈 경계 분리

CoreProcess는 창 생성 · 렌더러 생성 · 설정 로드 · 메타데이터 등록까지만 책임지고, Loop()는 순수 가상으로 비워 뒀습니다. 비워 둔 그 한 칸만 각자 구현합니다 — 툴은 패널을 그리는 루프, 런처는 매 프레임 씬을 갱신하는 루프입니다.

02

실행 단계별 인터페이스

시스템을 추가할 때마다 엔진의 등록표를 고쳐야 한다면 위 규칙은 지킬 수 없습니다. RegisterSystem<T>()가 T의 상속 관계를 컴파일 타임에 확인해, 해당 실행 단계 컨테이너에 직접 넣도록 했습니다.

SCENE 이 소유하는 것 entt::registry entt::dispatcher PhysicsScene multimap<name, SystemInfo> queue<entity> — 지연 삭제
한 프레임 — 순서는 코어가 정한다
핵심 코드 — 자동 등록
template <typename T> requires HasSystemTraits<T>
void Scene::RegisterSystem()
{
  constexpr auto name = SystemTraits<T>::name;
  if (_systemMap.contains(name)) return;   // 중복 방지

  auto system = std::make_shared<T>(*this);

  if constexpr (std::is_base_of_v<IUpdateSystem, T>) {
    _updates.push_back(system);
    _systemMap.insert({ name, { SystemType::Update,
                        _updates.size() - 1, systemId } });
  }
  // ... 8개 인터페이스에 대해 같은 블록
}
원칙과의 관계

새 시스템을 추가할 때 엔진 코드를 수정하지 않습니다. 필요한 인터페이스를 상속하고 매크로로 이름을 붙이면 실행 단계와 씬 저장, 툴의 시스템 목록에 함께 반영됩니다. 실행 순서는 어떤 인터페이스를 상속하느냐로 결정되므로 코어에 우선순위 값을 두지 않았습니다.

03

리플렉션 등록 일원화

컴포넌트가 늘 때마다 에디터와 직렬화를 함께 고쳐야 한다면 이것도 엔진 코드를 수정하는 일입니다. 둘이 서로를 참조하는 대신 같은 메타 컨텍스트를 읽게 했습니다. 수정할 파일은 게임 쪽 등록부 하나입니다.

핵심 코드 — 타입을 몰라도 되는 소비자
#define SET_DEFAULT_FUNC(class)              // 매크로 한 줄로
  .func<&core::AddComponent<class>>("AddComponent"_hs)
  .func<&core::RemoveComponent<class>>("RemoveComponent"_hs)
  .func<&core::GetHandle<class>>("GetHandle"_hs)
  .func<&core::SaveSnapshot<class>>("SaveSnapshot"_hs)
  // ... 프리팹 스냅샷까지 13개

// 코어·툴은 타입 이름을 모른 채 순회만 한다
for (auto&& [id, type] : entt::resolve(global::componentMetaCtx))
  if (auto save = type.func("SaveSnapshot"_hs))
    save.invoke({}, &snapshot, &archive);
왜 컨텍스트를 여러 개로 나눴나

전부 한 컨텍스트에 넣으면 인스펙터가 컴포넌트 목록을 뽑을 때 태그 · 레이어 · enum까지 섞여 나옵니다. 용도별로 컨텍스트를 나눠 순회 대상을 좁혔습니다. 별도의 필터 조건문이 필요 없습니다.

부수 효과
레이어 등록 매크로가 이름과 비트 마스크를 함께 심어 두기 때문에, 게임 코드는 충돌 판정을 비트가 아니라 이름으로 씁니다. 레이어 조합표도 툴에서 편집됩니다.
04

패널 간 이벤트 통신

패널이 서로를 직접 호출하면 하나를 고칠 때마다 다른 쪽이 깨집니다. 각 패널은 자기 그리기 함수와 디스패처만 가지고 있고, 나머지는 이벤트로 주고받습니다.

버스에 흐르는 것 OnToolSelectEntity OnToolModifyScene OnToolLoadScene OnToolLoadPrefab OnToolRemoveComponent OnToolPlayScene / StopScene
재생 · 정지 — 씬 직렬화를 되돌리기로 사용

에디터에서 게임을 재생하면 씬 상태가 되돌릴 수 없게 바뀝니다. 편집 상태를 복제하는 코드를 따로 넣는 대신 기존 씬 직렬화를 재사용했습니다. 정지는 임시 파일을 다시 여는 동작입니다.

에디터 때문에 코어에 추가한 기능은 거의 없습니다. 재생과 정지, 자동 저장 모두 게임이 쓰는 직렬화와 시간 배율을 조합해 만들었습니다.

대가

직렬화되지 않는 런타임 상태는 정지와 함께 사라집니다. 대신 재생 중 생성된 엔티티가 편집 상태에 남는 문제는 없었습니다.

05

의존 방향 정리

의존성은 아래로만 향합니다. 툴과 게임이 코어를 참조하고, 코어에는 그 반대 방향 참조가 없습니다. 덕분에 게임을 확장하는 동안 코어 파일을 수정할 일이 거의 없었습니다.
