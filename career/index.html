Midnight Cleanup

2024 G-STAR 전시
EnTT 기반 ECS 자체 엔진 · 대표 프로젝트
기간2024.04 – 2024.11 (7개월)
인원9명 · 프로그래밍 3 / 아트 3 / 기획 3
담당게임 엔진 · PhysX 물리 모듈 · 에디터 · 오브젝트 상호작용 / 청소 진행 로직
01프로세스 추상화 — 직전 엔진은 메인 루프가 고정돼 에디터와 런처가 각자 필요한 기능을 끼워 넣기 어려웠습니다. CoreProcess를 완전히 추상화해 ToolProcess·LauncherProcess가 각 실행 단위에 필요한 루프만 구현하도록 분리했고, 런처를 경량화하면서 코어와 응용 프로그램의 결합도를 낮췄습니다.
02조합형 컴포넌트로의 구조 개편 — 직전 엔진은 컴포넌트가 가상 함수를 가진 클래스여서 vtable 간접 호출로 ECS의 핵심 이점인 캐시 적중률을 살리지 못했습니다. 컴포넌트를 가상 함수 없는 순수 데이터로 개편하고, 공통 데이터(ColliderCommon)와 형태별 데이터(BoxCollider·SphereCollider)를 상속이 아닌 조합으로 분리해 데이터 중복과 vtable을 함께 제거했습니다.
03충돌 레이어 추상화 — 직전 엔진은 레이어를 코어에 박아 넣어 다른 프로젝트에서 재사용할 수 없었습니다. struct와 매크로로 앱마다 한 줄로 레이어를 정의하도록 바꾸고 비트마스크로 충돌을 필터링해, 코어를 고치지 않고도 범용성과 성능을 함께 확보했습니다.
04충돌 콜백 추상화 — 직전 엔진은 충돌 이벤트가 중앙에 집중돼 시스템별로 필요한 충돌만 받기 어려웠습니다. 필요한 시스템만 구독하도록 ICollisionHandler 인터페이스로 분산하고, PhysX API는 엔진 코어에만 은닉했습니다.
05리플렉션 에디터와 휴먼 에러 개선 — 직전 엔진은 파일명과 이벤트를 문자열로 직접 입력해 오타 오류가 잦았습니다. 리플렉션으로 가능한 입력을 콤보 박스로 전개하고 사전 정의 값을 엔진 리소스로 바꿔 런타임 편집을 지원함으로써, 기획·아트의 재컴파일과 실수를 제거했습니다.
06성능 최적화 — 프로파일링으로 다수 동적 광원의 그림자 렌더링이 병목임을 확인했습니다. 시연 일정상 엔진 수정이 어려워 활성 조명 수를 큐로 제한하는 자원 관리 시스템을 게임 로직 레벨에서 구현했고, 최저 프레임을 10FPS 이상 확보했습니다.
RESULT
기술 제약을 어두운 공간의 몰입감이라는 기획적 연출로 전환하며 성능을 확보했습니다. 직전 엔진의 한계를 구조 개편으로 풀어 7개월 팀 프로젝트로 완성했고 2024 G-Star 에 전시했습니다.

TicToc Guardians

2024 TGS 전시
커스텀 ECS 자체 엔진
기간2024.01 – 2024.02 (4주)
인원11명 · 프로그래밍 5 / 아트 3 / 기획 3
담당게임 엔진(커스텀 ECS · 리플렉션) · 에디터 · 리플레이 시스템
01커스텀 ECS 직접 구현 — ECS와 런타임 리플렉션을 라이브러리에 의존하지 않고 직접 만들어 개념을 체화하는 것을 목표로 삼았습니다. 데이터 인접성을 위해 타입별 고정 배열(std::array) 풀을 쓰되, 런타임 증설이 필요해 이를 std::list로 묶은 멀티 풀로 설계했습니다.
02포인터 주소 안정성 확보 — std::vector로 풀을 묶으면 증설 시 재할당으로 기존 컴포넌트 포인터가 무효화됩니다. 노드 기반인 std::list를 택해 풀을 증설해도 기존 노드 주소가 보존되게 했고, swap-pop 삭제 후에는 이동된 컴포넌트의 소유자 맵 포인터를 갱신해 일관성을 유지했습니다.
03C++20 채용 근거 — 모든 컴포넌트가 템플릿 기반 풀과 조회 경로를 거치는데, 잘못된 타입이 들어오면 해석하기 어려운 템플릿 오류가 발생합니다. C++20 concepts(requires IsComponent<T>)로 컴포넌트 타입만 허용하도록 제약해 오용을 컴파일 시점에 차단했고, 팀원이 ECS 위에서 안전하게 작업할 수 있게 했습니다.
04리플레이(고스트) 시스템 — 프레임 단위 입력을 비트셋으로 기록하고, 되감기 후 초기 상태로 되돌려 입력을 재주입하는 고스트 플레이어로 시간차 협동 퍼즐을 구현했습니다. 캐릭터와 리플레이어는 이벤트 버스로 통신해 결합도를 최소화했습니다.
RESULT
직접 구현을 통해 ECS의 한계를 체득했습니다. 컴포넌트가 가상 함수를 가진 클래스여서 vtable 간접 호출로 캐시 적중률을 온전히 살리지 못함을 확인했고, 이 경험이 다음 엔진에서 조합형 순수 데이터 컴포넌트로 개선하는 기준이 되었습니다. 2024 TGS 에 전시했습니다.

시작한 목적

C++ 자체 엔진으로 제작했던 《Fate Weaver》의 카드 조합에서 오는 재미를 제 방식으로 확장해 보고자, 팀 프로젝트가 끝난 뒤에도 같은 소재를 상용 엔진 위에서 다시 설계하고 있습니다. 기획부터 구현까지 직접 책임지며 게임 제작 전반을 보는 시야를 넓히는 것이 목표입니다.

배운 것

구조는 미루면 다음 작업이 막히고, 눈에 띌 때마다 손대면 진행 중인 작업이 흐트러졌습니다. 그래서 지금 하려는 일을 직접 막는 것만 바로 해결하고 나머지는 기록해 두었다가 나중에 다루는 기준을 세웠고, 지금은 이 기준이 리팩토링을 언제 시작하고 어디서 멈출지 판단하는 근거가 되고 있습니다.

01기획과 밸런스 — 전투 규칙과 카드·캐릭터 구조를 직접 정의하고, 초안을 기록·편집하는 저작 도구를 만들어 아이디어를 곧바로 반영했습니다. 수치는 감이 아니라 시뮬레이션으로 검증합니다.
02구조 설계 — 게임 규칙을 엔진에 의존하지 않는 순수 C# 코어에 두고 표현과 저작은 Unity 레이어로 분리했습니다. 새 효과와 상태는 핸들러 하나만 추가하면 되도록 해 콘텐츠가 늘어도 규칙 코드가 복잡해지지 않게 했습니다.
03AI 활용 원칙 — AI로 속도를 높이고 다양한 관점을 참고하되, 요구사항과 구조는 직접 정의하고 적용 여부와 범위는 제가 판단합니다. 그 기준이 흔들리지 않도록 아키텍처 경계는 문서로, 검증은 테스트로 저장소에 고정해 두었습니다.
RESULT
게임 하나를 AI와 함께 끝까지 완성해 가는 과정에서 기획·구현·검증을 아우르는 전체적인 시야를 넓혀 가고 있습니다.
