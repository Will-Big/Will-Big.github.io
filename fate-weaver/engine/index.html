2ND · FATE WEAVER (2023) — 설계 의도

오브젝트는 그릇,
기능은 컴포넌트

두 번째로 만든 자체 엔진입니다. 첫 엔진에도 구조는 있었지만 필요할 때마다 덧붙인 쪽에 가까웠고, 그때 구조를 먼저 설계하는 일의 중요성을 체감했습니다. 이번에는 협업의 기반이 되는 아키텍처를 먼저 세우고 시작했습니다. 엔진 아키텍처 설계와 구현 전반 — 오브젝트 관리, 씬 전환, 컴포넌트 시스템, 이벤트 메커니즘 — 을 담당했습니다.

설계 목표
필요한 주기만 돌고,
참조 없이도 말이 통하게

Unity 를 참고해 다형성과 템플릿으로 컴포넌트를 관리하는 컨테이너를 만들고자 했습니다. 모든 라이프사이클 함수를 강제로 호출하는 대신, 컴포넌트가 필요한 주기만 골라 참여하는 구조를 목표로 삼았습니다.

동시에 서로를 참조하기 어려운 클래스 사이의 통신을 중앙 집중형 이벤트로 해결하고, 엔진(Core)은 lib, 게임(App)은 exe 로 물리적으로 분리해 재사용성을 확보하려 했습니다.

01

실행 주기 인터페이스와 자동 등록

모든 컴포넌트가 Update·Render를 빈 함수로 들고 있는 대신, 필요한 인터페이스만 상속하게 했습니다. 등록은 사람이 하지 않습니다. AddComponent 안에서 dynamic_cast로 인터페이스를 확인하고, 해당하는 컨테이너에 알아서 담깁니다.

fate-weaver · Engine/GameObject.h — 등록과 순회
template<typename T>
T* GameObject::AddComponent()
{
    T* component = new T(this);
    m_Components.push_back(component);

    // 실행 주기별 컨테이너 등록
    if (IUpdatable* ua = dynamic_cast<IUpdatable*>(component))
        m_Updatables.push_back(ua);
    if (IFixedUpdatable* fua = dynamic_cast<IFixedUpdatable*>(component))
        m_FixedUpdatables.push_back(fua);
    if (IRenderable* ra = dynamic_cast<IRenderable*>(component))
        m_Renderables.push_back(ra);

    return component;
}

// GameObject.cpp — 해당 주기의 컨테이너만 순회한다
void GameObject::Update(const float& deltaTime)
{
    for (IUpdatable* ua : m_Updatables)
        ua->Update(deltaTime);
}
왜 인터페이스로 나눴나

컴포넌트가 늘어날수록 아무 일도 하지 않는 가상 함수 호출이 프레임마다 쌓입니다. 주기를 선언으로 드러내면 호출 자체가 없어지고, 컴포넌트를 보는 것만으로 언제 도는지 알 수 있습니다.

실제 결과
기대했던 만큼의 프레임 향상은 없었습니다. 다만 불필요한 호출을 구조적으로 막는다는 설계적 의미는 남았고, 상용 엔진이 왜 같은 방식을 쓰는지 이때 체감했습니다.
02

씬의 지연 처리

순회 도중에 오브젝트를 지우면 이터레이터가 깨집니다. 그래서 생성·삭제·씬 전환 요청을 큐에 쌓아 두고, 한 프레임의 모든 순회가 끝난 LateUpdate 시점에 한 번에 처리했습니다.

fate-weaver · Engine/SceneSystem.cpp — 미루고, 한 번에 처리한다
void SceneSystem::LateUpdate(const float& deltaTime)
{
    if (m_CurScene != nullptr)
        m_CurScene->LateUpdate(deltaTime);

    DelayedProcess();   // 순회가 모두 끝난 뒤에 큐를 비운다
}

void SceneSystem::DelayedDelete(std::any delGO)
{
    const auto go = std::any_cast<GameObject*>(delGO);
    go->SetAble(false);                                  // 즉시 비활성화
    m_Delayed.push({ delGO, SceneEvent::DELETE_EVENT }); // 삭제는 예약
}
03

중앙 집중형 이벤트 시스템

서로를 참조하기 어려운 클래스끼리 통신하도록, 이벤트를 엔진의 중앙 통로로 두었습니다. 게임 로직뿐 아니라 오브젝트 생성·삭제, 씬 전환 같은 엔진 내부 동작까지 이 통로로 요청합니다. 가장 신경 쓴 부분은 구독을 끊는 일을 사람이 기억하지 않게 만드는 것이었습니다.

fate-weaver · Engine/EventHandler.h — 구독 해지를 소멸자가 대신한다
class EventHandler
{
public:
    // 소멸 시 EventSystem 에 등록된 자신을 제거
    virtual ~EventHandler()
    {
        EventSystem::GetInstance()->RemoveListener(this);
    }

    // 멤버 함수를 std::function 으로 감싸 리스너 정보를 만든다
    template <typename T>
    ListenerInfo MakeListenerInfo(void (T::* func)(std::any))
    {
        static_assert(std::is_base_of_v<EventHandler, T>,
                      "T must be derived from EventHandler");
        return ListenerInfo(this,
            [this, func](std::any handler) { (static_cast<T*>(this)->*func)(handler); });
    }
};

이 구조가 남긴 아쉬움 — 문자열 이벤트 ID 와 std::any 파라미터 — 는 이후 엔진에서 타입 기반으로 바뀌었습니다. 그 변화를 이벤트 식별의 변화에서 따로 정리했습니다.

04

한계와 배운 점

세 가지가 남았고, 셋 다 다음 엔진의 목표가 되었습니다.

영역한계배운 점 · 이후 반영
실행 주기 최적화 인터페이스 분리가 기대만큼의 프레임 향상으로 이어지지는 않았습니다. 폭은 작았지만 불필요한 호출을 구조적으로 막는다는 설계적 의미가 남았습니다. 상용 엔진이 같은 방식을 쓰는 이유를 체감했습니다.
이벤트 시스템 std::any 는 유연했지만 수신측이 정확한 타입을 알고 캐스팅해야 했습니다. 식별자가 문자열이라 오타를 컴파일러가 잡지 못했고, EventHandler 상속과 MakeListenerInfo 사용이 강제되어 사용법이 복잡했습니다. 컴파일 타임에 오류를 검출하는 설계의 필요성을 절감했습니다. 이후 엔진에서 struct 자체를 이벤트 ID 이자 파라미터로 쓰는 방식으로 바꿨습니다 — 비교 보기
개발 생산성 오브젝트 위치와 속성 등 모든 게임 데이터를 코드로 관리했습니다. 사소한 수정에도 재컴파일이 필요했고, 개발 속도의 병목이 되었습니다. 코드와 데이터의 분리, 그리고 전용 에디터가 필수임을 배웠습니다. 다음 엔진의 최우선 목표가 되었습니다 — TicToc 엔진 설계
