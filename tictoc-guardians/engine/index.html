TICTOC ENGINE · EDITOR — 설계 의도

수치 하나를 고치려고
컴파일하지 않는다

세 번째로 만든 자체 엔진입니다. 이번에 새로 붙인 건 에디터였고, 그걸 만들려고 직렬화와 리플렉션을 처음 공부했습니다. 코어 구조도 거기에 맞춰 다시 잡았습니다. 지난 엔진에서 뭐가 불편했고 어디를 고쳤는지를 다이어그램으로 정리했습니다.

설계 원칙
게임의 값은 코드가 아니라
씬 파일에 있어야 한다

지난 팀 프로젝트를 하면서 정한 원칙입니다. 그때는 에디터가 없어서 오브젝트 위치도, 데미지 수치도 전부 코드 안의 숫자였습니다. 한 칸 옮기려고 값을 고치고, 컴파일을 기다리고, 게임을 처음부터 다시 켰습니다. 원하는 자리가 나올 때까지 이 과정을 여러 번 반복했습니다.

이번에는 그 반복을 없애는 게 목표였습니다. 값을 코드에서 꺼내 파일에 담으려면 직렬화가 있어야 했고, 어떤 타입이든 화면에 필드로 띄우려면 리플렉션이 있어야 했습니다. 아래는 이 두 가지를 어떻게 만들어 에디터에 붙였는지입니다.

01

수치 하나 고치는 데 걸리던 시간

지난 엔진에서는 값 하나를 확인하려고 여섯 단계를 거쳤습니다. 그중 다섯은 그냥 기다리는 시간이었습니다. 이번에는 고치는 곳과 확인하는 곳이 같은 화면입니다.

02

에디터와 런처가 같은 게임 코드를 쓴다

Play 버튼이 제 역할을 하려면 에디터가 게임을 직접 돌릴 수 있어야 했습니다. 그래서 게임 프로젝트를 라이브러리로 만들고, 에디터와 런처가 각자 그걸 상속하게 했습니다. EditorProcess에서 새로 쓴 건 OnImGuiRender()와 편집 모드용 Update() 두 개뿐입니다.

그래서 에디터의 Play는 별도의 미리보기가 아니라 런처와 똑같은 코드를 돌립니다. 런처가 매 프레임 부르는 Update()를 그대로 부르고, 편집 중일 때만 변환 갱신과 입력 처리로 바꿔 끼웁니다.

대가

창 생성부터 에디터 이벤트 구독까지 코어가 다 떠맡아서 GameProcess가 계속 커졌습니다. 실행 방식만 비워 두는 구조는 다음 엔진에서야 정리했습니다.

03

컴포넌트 저장 — 타입마다 풀, 풀은 목록으로

컴포넌트를 어디에 둘지 정하는 일이 ECS의 출발점이었습니다. 타입마다 풀을 하나 두고, 풀이 차면 목록에 풀을 하나 더 붙이는 방식으로 만들었습니다. 대신 지울 때 빈 자리를 메우느라 컴포넌트의 주소가 바뀌므로, 그 주소를 들고 있던 쪽을 찾아 고쳐 주어야 했습니다.

하는 일맡은 자료 구조동작
저장ComponentPool<T, N> — 배열과 활성 경계경계 위치를 하나 늘리고 그 칸의 주소를 돌려준다
검색map<GameObjectId, map<Uid, Component*>>오브젝트 번호로 한 번, 컴포넌트 번호로 한 번 조회한다 — 컴포넌트 번호는 타입 이름을 컴파일 타임에 접은 CRC32다
삭제ComponentPoolManager::Release마지막 활성 원소를 빈 자리로 옮기고 경계를 되돌린다 — 그래서 빈 풀이 되면 목록에서 반납한다
순회System::ComponentItr<T>풀마다 활성 구간만 모아 시스템에 넘긴다 — 시스템은 범위 기반 for 한 줄로 돈다
삭제와 포인터 보정
왜 std::vector 대신 std::list 와 std::array 를 사용했나

vector 는 늘어날 때 재할당이 일어납니다. 그 순간 이미 나눠 준 컴포넌트 포인터가 한꺼번에 무효가 됩니다. 대신 array 로 같은 타입을 붙여 두어 순회 이점을 얻고, 그 배열을 list 로 이어 풀을 늘려도 앞선 풀의 주소가 그대로 남게 했습니다.

막혔던 지점
컴포넌트를 가리키는 것이 주소뿐이어서, 그 주소가 풀의 몇 번째 칸인지 되짚을 수단이 없었습니다. 그래서 삭제할 때마다 풀을 앞에서부터 훑으며 활성 원소의 주소를 대조했고, 지우는 비용이 살아 있는 컴포넌트 수에 비례했습니다. 그때 제가 한 일은 Release 가 이사 온 컴포넌트의 주인 번호를 돌려주게 해서 색인이 깨지는 것만 막은 것이었고, 탐색 자체는 손대지 못했습니다.
원인은 다음 엔진에서 EnTT 의 저장 구조를 뜯어보고서야 정확히 짚었습니다. 번호에서 배열 위치로 가는 색인을 자료 구조가 함께 들고 있으면 훑을 일이 없다는 것이었습니다. 빈 자리를 마지막 원소로 메우는 흐름은 제 구현과 같았고, 찾는 방법만 달랐습니다. 그래서 이후에는 컴포넌트를 주소로 들고 다니지 않고 엔티티 번호로 다루도록 바꿔, 조회를 제 코드가 아니라 자료 구조가 책임지게 했습니다.
04

리플렉션 — 등록은 미리, 조회는 이름으로

인스펙터가 어떤 컴포넌트든 그려내려면 멤버 이름과 타입, 그 멤버까지 닿는 길이 실행 중에도 남아 있어야 합니다. 매크로 두 줄이 클래스에 등록 코드를 심어 두고, 프로그램이 로드될 때 TypeInfo가 채워지게 했습니다.

핵심 코드 — 멤버 포인터를 들고 있는 핸들러
struct Transform : public Component
{
  GENERATE_CLASS_TYPE_INFO(Transform)   // 타입 등록

  VSM::Vector3 LocalPosition;
  PROPERTY(LocalPosition)               // 멤버 등록
};

// 핸들러가 멤버 포인터를 캡슐화한다 — 이름 조회 후엔 직접 참조
template <typename TClass, typename T>
ElementType& PropertyHandler<TClass, T>::Get(void* object) const
{
  return static_cast<TClass*>(object)->*m_ptr;
}
왜 정적 등록인가

C++에는 실행 중에 타입을 훑을 방법이 없습니다. 그래서 클래스가 로드될 때 등록을 다 끝내 두고, 실행 중에는 이름으로 찾아 캐스팅만 합니다. 비용이 찾는 순간에만 생깁니다.

부수 효과
매크로를 누락해도 컴파일은 그냥 통과합니다. 실행해서 인스펙터를 열어 봐야 필드가 없다는 걸 알게 됩니다. 매크로에 의존하는 게 이 구조의 제일 큰 약점이었습니다.
05

인스펙터 — 타입을 보고 위젯을 고른다

인스펙터 코드에는 컴포넌트 이름이 한 번도 나오지 않습니다. 선택한 오브젝트에 붙은 컴포넌트를 훑고, 각 Property의 타입 해시를 보고 위젯을 고릅니다. 앞에서 말한 반복을 실제로 없앤 화면이 여기입니다.

핵심 코드 — 타입 하나에 위젯 하나
template <typename T>
void MatchGuiByType(const Property* property, Component* component)
{
  const auto name = property->GetName();
  T& val = property->Get<T>(component);   // 참조를 받는다

  if constexpr (std::is_same_v<T, VSM::Vector3>)
    ImGui::DragFloat3(name, &val.x);
  else if constexpr (std::is_same_v<T, VSM::Quaternion>) {
    Vector3 euler = val.ToEuler() / (XM_PI / 180.f);
    ImGui::DragFloat3(name, &euler.x);   // 사람은 각도로 본다
    val = Quaternion::CreateFromYawPitchRoll(euler * (XM_PI / 180.f));
  }
  // ... bool · float · string · enum 들
}
막혔던 지점

타입과 위젯을 잇는 걸 결국 손으로 쓴 분기문으로 해결했습니다. 타입이 하나 늘 때마다 인스펙터를 다시 열어야 했고, 처리해 두지 않은 타입은 Unreflected Type이라는 글자만 남았습니다. 애니메이션 클립 같은 건 결국 파일 이름을 손으로 타이핑해서 넣었습니다.

그래서 다음 엔진에서는
타입 정보에 범위와 설명, 기본 함수까지 같이 등록해 두고, 모르는 타입은 구조체로 보고 재귀로 내려가게 바꿨습니다 → Midnight Cleanup의 메타 허브
06

직렬화 — 씬과 프리팹, 그리고 되돌리기

저장 단위를 두 개로 나눴습니다. 씬은 컴포넌트 풀을 통째로 타입 이름 아래에 쓰고, 프리팹은 오브젝트 하나와 그 자식들만 재귀로 씁니다. 이 차이 때문에 컴포넌트마다 SerializePool과 SerializeThis를 따로 뒀습니다.

Play · Stop — 되돌리기를 직렬화로 해결했다

에디터에서 게임을 한 번 돌리면 씬 상태가 망가집니다. 편집 상태를 복제하는 코드를 새로 쓰는 대신, 이미 만들어 둔 씬 저장·로드를 되돌리기로 썼습니다. Stop은 임시 파일을 다시 여는 것뿐입니다. 창을 켜 둔 채로 값을 고치고 바로 돌려 보게 된 게 이 지점입니다.

직렬화를 먼저 만들어 둔 덕에 Play·Stop·프리팹·씬 저장이 다 같은 코드를 씁니다. 에디터 때문에 코어에 새로 넣은 건 시간 배율과 리셋 정도입니다.

대가

저장되지 않는 런타임 상태는 Stop과 함께 날아갑니다. 리셋과 로드 사이에 풀이 다시 만들어지니, 들고 있던 Component*는 그 순간 전부 버려야 했습니다.

07

창 다섯 개와 이벤트 하나

창은 IWindow::OnImGuiRender() 하나만 구현하면 목록에 들어갑니다. 창이 코어에 부탁할 일은 문자열 키 이벤트로 보냈습니다. 삭제처럼 순서가 중요한 건 지연 이벤트로 넘겼는데, 그리는 도중에 대상이 사라져서 터진 적이 있었기 때문입니다.

버스에 흐르는 것 OnPlayButton OnStopButton OnLoadScene OnStart OnDeleteGameObject / OnDeleteComponent — 지연 OnSetSpeedWeight
08

남은 것과 넘긴 것

컴파일 왕복은 없앴지만, 대신 에디터 코드를 고치는 왕복이 생겼습니다. 타입이 늘면 인스펙터 분기를, 멤버가 늘면 등록 매크로를 사람이 챙겨야 했습니다. 아래 목록이 다음 엔진에서 먼저 손본 부분입니다.

남은 문제이번 엔진에서는다음 엔진에서는
등록 누락매크로를 누락해도 컴파일은 통과, 실행 후 발견등록부를 한 파일로 모으고 기본 함수까지 매크로가 함께 심는다
타입 분기타입 해시를 손으로 나열, 모르는 타입은 표시 불가모르는 타입은 구조체로 보아 재귀 · 범위와 설명을 메타에서 읽는다
프로세스 비대화코어가 창 · 이벤트 · 실행 방식을 한곳에서 처리코어는 초기화만, 실행 방식은 순수 가상으로 비워 둔다
참조 안정성풀의 swap-pop 후 엔티티 맵의 포인터를 손으로 보정검증된 ECS 라이브러리로 옮기고 핸들로 접근한다
이벤트 키문자열 키 — 오타를 컴파일러가 잡지 못한다타입으로 구분되는 디스패처, 툴 전용 버스를 코어와 분리

그래도 이 엔진에서 얻은 건 분명합니다. 기획과 아트가 값을 직접 만진 첫 엔진이었고, 이후에 만든 도구는 전부 직렬화와 리플렉션 위에 올라갔습니다. 툴을 처음 접한 동료가 사용하기 쉽도록 에디터 설명서를 따로 써서 같이 넘겼습니다.
