01

순수 C# 코어와 Unity 레이어의 분리

이 프로젝트의 전제

AI가 Unity 에디터를 열지 않고 헤드리스로 작업하며 dotnet test로 직접 검증할 수 있도록, 게임 규칙은 UnityEngine을 참조하지 않는 순수 C# 코어에 두고 표현과 저작은 Unity 레이어에 두었습니다.

대신 코어가 Unity 레이어의 에셋을 읽을 수 없으므로, 카드 능력은 SO로 저작한 뒤 코드로 변환해 코어에 넘기는 방식을 택했습니다. 이 선택이 뒤에 문제가 되었습니다.

02

구조 전환 사례

사례 1 저작 파이프라인

카드 저작 원본의 단일화

같은 데이터가 두 곳에 있던 상태를 JSON 하나로 좁힌 과정입니다.

이 게임은 카드 데이터가 자주 바뀝니다. 그래서 카드 한 장을 파일 하나로 두고, 그 파일을 런타임에 읽어 들이는 저작 방식을 처음부터 예정하고 있었습니다. SO 저작을 제안받았을 때도 그 전제를 감안한 안이라고 보고 그대로 받았습니다.

개선 전 저작 경로
인스펙터에서 SO 저작  →  CardCodeGenerator  →  생성된 C# 리터럴  →  헤드리스 시뮬레이션

카드는 인스펙터에서 ScriptableObject로 저작하고, 에디터 메뉴의 CardCodeGenerator가 그 내용을 순수 C# 리터럴로 뽑아냈습니다. 헤드리스 테스트는 이 과정에서 생성된 코드를 사용했습니다. 저작에 SO가 반드시 포함되어야 했으므로 같은 데이터가 SO와 리터럴 코드로 병존했습니다.

직렬화를 붙이려고 작업을 시작하자 SO는 에디터에서만 생성할 수 있어 런타임 생성이 어렵고, 데이터를 파일 단위로 늘리기도 JSON보다 번거롭다는 답이 돌아왔습니다. 제가 예정하고 있던 두 가지가 모두 SO로는 어려운 일이었으나, 그 계획을 밝히지 않았으므로 설계에 반영될 수 없었습니다.

전환 순서

원본을 JSON 하나로 옮기기로 하고, 순서를 다음과 같이 잡았습니다.

07-31 직렬화 설정과 다형 컨버터, 로더를 만들고 JSON 왕복을 테스트로 고정
07-31 카드 콘텐츠를 JSON으로 내보내고 옛 원본과 결과가 같다는 것을 테스트로 잠금
08-02~03 상태 · 덱 · 풀 · 캐릭터 콘텐츠를 옮기고, 전투 씬이 JSON을 읽도록 전환
08-03 카드 SO 제거 — 97개 파일, 2,528줄 삭제
08-03 코드 생성 경로 제거 — CardCodeGenerator.cs 698줄 삭제
08-05 카드 규칙의 C# 원본을 지우고 JSON을 유일 원본으로 확정

원본이 둘인 동안에는 한쪽만 고쳐도 컴파일이 통과하므로, 두 원본이 같은 결과를 낸다는 것을 테스트로 고정한 뒤에 런타임을 옮기고 마지막에 옛 경로를 지웠습니다.

같은 카드의 전환 전후

시작 덱의 견제타는 피해 4와 방어 1을 함께 가진 카드입니다. 전환 전에는 인스펙터에서 저작한 SO를 CardCodeGenerator가 아래 한 줄로 옮겼고, 헤드리스 테스트는 그 줄을 읽었습니다.

개선 전 — Assets/Core/Simulation/Generated/GeneratedCards.cs

규칙 반영

콘텐츠의 원본은 JSON 하나이고 SO 카드 저작 경로는 없으며 남아 있는 ScriptableObject는 표현 자원 전용으로 규칙 수치를 담지 않는다는 것을 조항으로 적어, 지운 구조가 다시 들어오지 않도록 했습니다.

얻은 기준

알고 있는 전제라도 명시하지 않으면 설계에 반영되지 않으며, 받은 구조는 그 자리에서 한 번 더 확인해야 한다는 것을 얻었습니다.

사례 2 설계 문서

설계 문서 형식의 개편

같은 형태를 한 번 더 겪고, 원인을 문서의 형식에서 찾은 과정입니다.

이 게임은 카드에 들어가는 데이터가 유동적이어서 카드 타입 설계가 중요했습니다. 요구사항과 확장 방향은 충분히 설명했다고 보았으므로 확장을 감안한 설계가 나왔으리라 생각해 계획서를 자세히 확인하지 않았습니다.

실제로 그 부분을 확장할 때가 되어서야 해당 지점이 하드코딩되어 있는 것을 확인했고, 받은 구조를 한 번 더 확인해야 한다고 정리해 두고도 같은 일이 되풀이되었으므로 설계 검토를 소홀히 한 제 문제로 보았습니다.

검토가 이루어지지 않은 원인

제가 읽고 있던 계획서는 다음 세션의 AI가 그대로 실행할 수 있도록 쓰인 문서였고, 분량과 세부가 실행에 맞춰져 있어 사람이 검토하기에는 부담이 컸습니다. 문제는 검토를 게을리한 태도가 아니라 검토할 수 없는 형식이었습니다.

설계 문서의 이층 구조

설계 개요 (사람 검수용)

60줄을 넘기지 않으며, 코드와 알고리즘 설명 대신 어떤 객체가 무엇에 의존하는지만 씁니다.

상세 (세션 인계용)

실행에 필요한 근거는 여기에만 둡니다. 개요로 승인을 받고 상세로 구현합니다.

개요에는 “이 선택으로 나중에 어려워지는 것” 칸을 두고 비워 둘 수 없게 했는데, 앞 사례의 런타임 생성 제약처럼 알고 있었어야 할 제약이 전달되지 않는 자리가 그 칸이기 때문입니다.

하드코딩 제거 방향

고정된 분류를 지우고 데이터에서 파생시키는 쪽으로 정리해, CardType 스키마를 제거하고 대상 규칙을 카드에서 떼어 질의로 바꾸었으며 개입은 액션별 스펙으로 나눴습니다.

확장하려던 것은 피해와 방어를 함께 가진 카드였는데, 카드의 성질이 Attack · Skill · Defense 중 하나로 고정되어 있어 어느 쪽으로 적어도 맞지 않았습니다. “앞서 실행되는 적의 공격 카드”처럼 성질을 묻는 조건들이 이 분류를 직접 비교하고 있었으므로, 분류를 어느 쪽으로 정하든 판정이 어긋났습니다.

개선 전 — Assets/Core/Cards/CardType.cs · Core/Conditions/
public enum CardType
{
    Attack,
    Skill,
    Defense
}

// 조건이 카드의 분류를 직접 받는다
public sealed record AdjacentCardIs(
    AdjacentDirection Direction,
    Side Side,
    CardType? Type = null) : Condition;

// ConditionEvaluator — 앞서 실행되는 적의 공격 카드가 있는가
if (earlier.Def.Side == Side.Enemy && earlier.Def.Type == CardType.Attack)
지금 — Assets/Core/Cards/CardDefinition.cs · Core/Conditions/
// CardDefinition — 무엇으로 분류되는지가 아니라 무슨 효과를 가졌는지를 묻는다
public bool HasEffect(EffectKey key)

public sealed record AdjacentCardHasEffect(
    AdjacentDirection Direction,
    Side Side,
    EffectKey EffectKey) : Condition;

// ConditionEvaluator — 같은 질문을 효과로 판정한다
if (earlier.Def.Side == Side.Enemy
    && earlier.Def.HasEffect(EffectKeys.Damage))

피해 카드인지는 카드가 든 효과가 정하므로 피해와 방어를 함께 가진 카드도 양쪽 조건에 모두 걸리고, 효과를 더할 때 고쳐야 할 분류 목록이 없습니다. 개입 쪽도 같은 방식으로, 액션마다 다른 파라미터를 카드의 고정 칸이 아니라 액션별 스펙이 갖도록 옮겼습니다.

개편 이후의 절차

현재는 개요를 검토해 승인한 뒤 구현으로 넘어갑니다.

03

두 사례를 기반으로 한 저작 구조의 개선

이전
SO 에셋
→ CardCodeGenerator
→ 생성된 C#
→ 코어
지금
Content/Cards/<카드>.json
→ ContentBootstrap.Load
→ 코어

카드 데이터를 SO와 리터럴 코드가 중복해서 가지고 있던 구조에서 JSON 단일 소유 구조로 개편하였고, 새로운 기능의 추가 또한 핸들러 클래스 추가와 키 등록으로 간소화하였습니다.
