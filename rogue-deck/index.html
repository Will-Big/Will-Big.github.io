턴제 덱빌딩 로그라이크입니다. 실행 카드는 매 턴 자동으로 뽑혀 자동으로 발동되고, 플레이어가 직접 쓰는 것은 실행선에 늘어선 그 순서를 바꾸는 조작 카드입니다. 적의 다음 수까지 모두 공개된 채로 턴이 시작되므로, 카드 한 장의 수치보다 순서와 조건과 상태가 서로를 참조하며 만들어 내는 판정이 규칙의 대부분을 차지합니다. 구현은 AI와 나눠 맡고 있으며, 무엇을 맡기고 어떤 구조를 지킬지는 저장소의 규칙 문서(AGENTS.md · 조항 30개)로 정해 두었습니다.

01

순수 C# 코어와 Unity 레이어의 분리

이 구조를 택한 이유

카드 밸런스를 수기 시뮬레이션으로 확인하던 것을 코드로 반복 실행하는 것과, Unity를 쓰되 AI가 에디터를 열지 않고 규칙 코드를 다룰 수 있게 하는 것이 이 프로젝트의 두 요구였습니다. 두 요구가 같은 구조를 가리켰으므로 게임 규칙은 UnityEngine을 참조하지 않는 순수 C# 코어에 두고, 표현과 저작은 Unity 레이어에 두었습니다.

엔진을 쓰지 않겠다는 것이 아니라 규칙 레이어만 순수하게 두는 선택이며, 대가는 코어가 Unity 에셋을 직접 읽지 못해 경계에서 변환이 필요하다는 것입니다. 그래서 카드 능력은 SO로 저작한 뒤 코드로 변환해 코어에 넘기는 방식으로 시작했습니다.

02

효과 하나를 늘릴 때 손대는 곳

카드 효과는 종류가 계속 늘어나므로, 새 효과를 넣을 때 기존 코드를 열지 않는 것을 저장소 규칙으로 두었습니다.

AGENTS.md 조항 9

“확장은 레지스트리로 한다. 새 효과/상태 이상/개입 액션 = 핸들러 클래스 1개 + 키 등록. 중앙 switch를 키우지 않는다.”

시작 덱의 증류는 적의 독을 1 소비하고 다시 걸어, 소비에 성공했을 때만 다음 턴 운명력을 1 더 주는 카드입니다. 마지막 효과인 다음 턴 운명력을 새로 넣는다고 하면, 손대는 곳은 네 군데입니다.

효과 하나가 지나가는 경로

기존 파일을 여는 것은 카드 JSON과 키 목록과 등록 목록의 각 한 줄뿐이고, 효과가 무엇을 하는지는 전부 새 파일 안에 있습니다. 핸들러가 지켜야 하는 계약은 셋입니다.

Assets/Core/Effects/IEffectHandler.cs
public interface IEffectHandler
{
    EffectKey Key { get; }                                            // 어떤 효과인가
    CardTargetKey? TargetFor(CardDefinition card, EffectData effect);  // 대상이 필요한가
    void Apply(EffectContext ctx);                                    // 무엇을 하는가
}

다음 턴 운명력의 경우 Apply의 본체는 전투 상태에 값을 적립하는 한 줄이고, 실제 지급은 턴을 시작하는 쪽이 맡습니다. 키인 EffectKey는 enum이 아니라 문자열을 감싼 읽기 전용 구조체라, 값이 늘어도 닫힌 목록을 고칠 일이 없으면서 타입은 구분됩니다.

키와 핸들러를 담는 EffectRegistry는 Dictionary 하나이며 분기가 없으므로, 효과가 늘어도 커지는 파일은 없습니다. 상태 이상과 조작 카드의 액션도 각자의 레지스트리로 같은 형태를 씁니다.

이 경로의 첫 칸이 카드 파일 한 줄인 것은 카드 데이터의 원본이 JSON 하나이기 때문입니다. 전에는 같은 데이터가 ScriptableObject와 거기서 뽑아낸 C# 코드에 나뉘어 있어, 효과 하나를 늘리려면 인스펙터에서 저작하고 코드를 다시 생성해야 했습니다. 원본을 하나로 좁힌 과정은 뒤의 사례 1 — 카드 저작 원본의 단일화에 있습니다.

03

시나리오 비교 러너

코어가 UnityEngine을 참조하지 않으므로 씬을 띄우지 않고 콘솔에서 같은 규칙을 돌릴 수 있고, 코어가 내놓는 것이 이벤트 타임라인 하나뿐이므로 그 타임라인을 화면 대신 텍스트로 재생할 수 있습니다. 그 위에 같은 시나리오를 조작 없이 한 번, 조작을 넣어 한 번 돌려 두 결과를 비교하는 러너를 두었습니다.

같은 판을 두 번 돌린다

리포트는 턴마다 Initial order와 Resolved order를 실행 순서 번호와 함께 찍고, 카드별 조건 판정과 피해를 이어 붙입니다. 순서 조작이 이 게임의 주제이므로 출력 형식이 곧 도메인의 형태입니다.

적이 먼저 해결되어 두 조건이 함께 성립하지 못하는 배치이며, 조작으로 적을 늦추면 같은 카드가 조건을 채웁니다. 위 값은 DesignInvariantTests에 단언으로 고정되어 있습니다.

04

구조 전환 사례

사례 1 저작 파이프라인

카드 저작 원본의 단일화

같은 데이터가 두 곳에 있던 상태를 JSON 하나로 좁힌 과정입니다.

이 게임은 카드 데이터가 자주 바뀌므로 카드 한 장을 파일 하나로 두고 런타임에 읽어 들이는 저작 방식을 처음부터 예정하고 있었으나, 그 계획을 밝히지 않은 채 SO 저작안을 받았습니다.

개선 전 저작 경로
인스펙터에서 SO 저작  →  CardCodeGenerator  →  생성된 C# 리터럴  →  헤드리스 시뮬레이션

카드는 인스펙터에서 ScriptableObject로 저작하고, 에디터 메뉴의 CardCodeGenerator가 그 내용을 순수 C# 리터럴로 뽑아냈습니다. 헤드리스 시뮬레이션은 이 과정에서 생성된 코드를 사용했습니다. 저작에 SO가 반드시 포함되어야 했으므로 같은 데이터가 SO와 리터럴 코드로 병존했습니다.

직렬화를 붙이려고 작업을 시작하자 SO는 에디터에서만 생성할 수 있어 런타임 생성이 어렵고, 데이터를 파일 단위로 늘리기도 JSON보다 번거롭다는 답이 돌아왔습니다. 제가 예정하고 있던 두 가지가 모두 SO로는 어려운 일이었으나, 밝히지 않은 계획은 설계에 반영될 수 없었습니다.

전환 순서

원본이 둘인 동안에는 한쪽만 고쳐도 컴파일이 통과하므로, 두 원본이 같은 결과를 낸다는 것을 먼저 테스트로 고정한 뒤 런타임을 JSON으로 옮기고 마지막에 옛 경로를 지웠습니다. 이 과정에서 카드 SO 97개 파일 2,528줄과 CardCodeGenerator.cs 698줄이 삭제되었고, 2026-08-05에 JSON이 유일 원본으로 확정되었습니다.

같은 카드의 전환 전후

시작 덱의 견제타는 피해 4와 방어 1을 함께 가진 카드입니다. 전환 전에는 인스펙터에서 저작한 SO를 CardCodeGenerator가 아래 한 줄로 옮겼고, 헤드리스 시뮬레이션은 그 줄을 읽었습니다.

개선 전 — Assets/Core/Simulation/Generated/GeneratedCards.cs
// AUTO-GENERATED — SO에서 뽑아낸 코드이며 사람이 손대는 자리가 아닙니다.
new CardSpec { Id = "probing_strike", Name = "견제타", EnergyCost = 1, BaseExecutionOrder = 4, InterventionEffectValue = 0, Effects = new EffectSpec[] { new DamageSpec { Value = 4, Selector = TargetSelectorRef.FrontMost, Condition = new ConditionSpec { … } }, new ApplyStatusSpec { Status = new StatusKeyRef { Id = "block" }, Count = 1, Target = StatusApplyTarget.Self, Condition = new ConditionSpec { … } } } },

조건 부분만 줄인 것이고 줄바꿈은 없습니다 — 카드 한 장이 실제로 이 한 줄입니다. 자동 생성된 코드라 동작에 필요한 요소가 기본값까지 남김없이 펼쳐져 있고, 컴파일 시점에 고정되므로 런타임에는 고칠 수 없었습니다.

지금 — Assets/StreamingAssets/Content/Cards/probing_strike.json
"id": "probing_strike",
"name": "견제타",
"energyCost": 1,
"baseExecutionOrder": 4,
"effects": [
  { "kind": "damage", "value": 4, "selector": "FrontOne" },
  { "kind": "apply_status", "status": "block", "count": 1 }
]

기본값은 적지 않으므로 카드에 실제로 저작된 것만 남고, 카드 한 장이 파일 하나입니다. 효과 두 개를 각각 한 줄로 접고 바깥 괄호와 grade·tags는 줄였습니다. 전투 씬과 헤드리스 시뮬레이션이 모두 ContentBootstrap.Load로 이 파일을 읽습니다.

규칙 반영

콘텐츠의 원본은 JSON 하나이고 SO 카드 저작 경로는 없으며 남아 있는 ScriptableObject는 표현 자원 전용으로 규칙 수치를 담지 않는다는 것을 조항으로 적어, 지운 구조가 다시 들어오지 않도록 했습니다.

얻은 기준

알고 있는 전제라도 명시하지 않으면 설계에 반영되지 않으며, 받은 구조는 그 자리에서 한 번 더 확인해야 한다는 것을 얻었습니다.

사례 2 설계 문서

설계 문서 형식의 개편

같은 형태를 한 번 더 겪고, 원인을 문서의 형식에서 찾은 과정입니다.

카드에 들어가는 데이터가 유동적이어서 카드 타입 설계가 중요했으나, 요구사항을 충분히 설명했다고 보아 계획서를 자세히 확인하지 않았습니다. 확장할 때가 되어서야 그 지점이 하드코딩된 것을 확인했고, 앞 사례에서 받은 구조를 한 번 더 확인하기로 정리해 두고도 같은 일이 되풀이되었으므로 처음에는 제 검토 문제로 보았습니다.

검토가 이루어지지 않은 원인

제가 읽고 있던 계획서는 다음 세션의 AI가 그대로 실행할 수 있도록 쓰인 문서였고, 분량과 세부가 실행에 맞춰져 있어 사람이 검토하기에는 부담이 컸습니다. 문제는 검토를 게을리한 태도가 아니라 검토할 수 없는 형식이었습니다.

설계 문서의 이층 구조

설계 개요 (사람 검수용)

60줄을 넘기지 않으며, 코드와 알고리즘 설명 대신 어떤 객체가 무엇에 의존하는지만 씁니다.

상세 (세션 인계용)

실행에 필요한 근거는 여기에만 둡니다. 개요로 승인을 받고 상세로 구현합니다.

개요에는 “이 선택으로 나중에 어려워지는 것” 칸을 두고 비워 둘 수 없게 했는데, 앞 사례의 런타임 생성 제약처럼 알고 있었어야 할 제약이 전달되지 않는 자리가 그 칸이기 때문입니다.

하드코딩 제거 방향

고정된 분류를 지우고 데이터에서 파생시키는 쪽으로 정리해, CardType 스키마를 제거하고 대상 규칙을 카드에서 떼어 질의로 바꾸었으며 조작 쪽은 액션별 스펙으로 나눴습니다.

같은 조건을 판정하는 방식 — 앞서 실행되는 적의 공격 카드가 있는가
개선 전 — 분류로 묻는다
earlier.Def.Type == CardType.Attack

카드의 능력이 Attack · Skill · Defense 세 값으로 닫혀 있고, 조건 객체가 그 분류를 직접 받았습니다. 분류에 없는 능력이 생기면 enum부터 고쳐야 합니다.

지금 — 효과로 묻는다
earlier.Def.HasEffect(EffectKeys.Damage)

무엇으로 분류되는지가 아니라 무슨 효과를 가졌는지를 묻습니다. 효과가 늘어도 코어를 고칠 일이 없고, 키는 앞 절의 EffectKey와 같은 것입니다.

조작 쪽도 같은 방식으로, 액션마다 다른 파라미터를 카드의 고정 칸이 아니라 액션별 스펙이 갖도록 옮겼습니다.

개편 이후의 절차

현재는 개요를 검토해 승인한 뒤 구현으로 넘어갑니다.
